# flight-tracker-api

The main API: flight lifecycle, briefing, SimBrief import, live position relay, the Discord bot and scheduled jobs, for the MyPreflight web app and the Transponder.

Last reviewed: 2026-11-01

## Repo-specific notes

Anything about the product or business belongs in the knowledge base; this file keeps the engineering detail specific to this repo.

- Run locally: `cp .env.dist .env`, then `docker compose up -d --build`. Packages, database schema and seed data are set up automatically. API docs are at <http://localhost/api>.
- Test: `docker compose exec app npm run format`, then `npm run lint` and `npm run test:functional` (cucumber-js, `features/`) the same way. These are the steps CI runs.
- Deploy: bump `package.json` `version` in every PR. Merging to `main` tags the version, pushes the image to GitHub Container Registry and deploys it to DigitalOcean.
- Links in Discord messages and emails are `FRONTEND_BASE_URL` plus a path from the web app's route table (`app/routes.ts` in `mypreflight/app`). In production the variable lives only in the DigitalOcean app spec, and nothing here fails when the app renames a route, so check both when a link 404s.

When your change alters product behaviour, also open a PR to the knowledge base updating the matching file. When it ships something a pilot will notice, also open a PR to [mypreflight/landing](https://github.com/mypreflight/landing) adding a changelog entry with before and after screenshots; that repo's `AGENTS.md`, under "Changelog", says how.

## Commands

**Never run `npm` or `npx` on the host.** The dev environment is fully Dockerized (`compose.yaml` + `docker/dev/entrypoint`), and the bind-mounted `./node_modules` plus Prisma engines will break if you mix host-arch installs in. Always execute inside the `app` service.

Bring the stack up first — the entrypoint runs `npm install`, `prisma generate`, migrate, seed, and `start:dev` automatically:

- `docker compose up -d --build` — app on `:80` → container `:3000`, plus Postgres and one `mock` container (Mockoon) serving every external provider on ports `1080`–`1089`.
- `docker compose logs -f app` — tail the Nest dev server.

Everything else runs via `docker compose exec app …` (stack up) or `docker compose run --rm app …` (one-off):

- `docker compose exec app npm run lint` / `lint:fix` — ESLint over `{src,features,prisma,test}/**/*.ts`.
- `docker compose exec app npm run format:fix` — Prettier (includes Gherkin + Prisma plugins).
- `docker compose exec app npm run build` — Nest build to `dist/`.
- `docker compose exec app npm test` — Jest (`jest.config.js`, ts-jest; `tsconfig.build.json`). Colocated `*.spec.ts` unit tests exist (e.g. the `report-*` command and `detect-*` listener specs under `src/modules/flights/`); broader behavior coverage still lives in Cucumber.
- `docker compose exec app npm run test:functional` — Cucumber. `cucumber.js` loads step definitions from `features/_context/**/*.ts` and sets `failFast: true`. The database context truncates every table and reseeds in `BeforeAll`, so the suite destroys and reseeds the DB — don't run it against a database you care about.
- Single feature: `docker compose exec app npx cucumber-js features/airport/airport.list.feature`. Filter by scenario name: `--name "cabin crew"`.
- `docker compose exec app npm run database:seed` — **destructive** `prisma db push --force-reset` + seed (`prisma/seed/seed.ts`).
- `docker compose exec app npm run database:reset` — force-reset schema, no seed.
- `docker compose exec app npm run database:migrate` — `prisma migrate deploy`.
- `docker compose exec app npx prisma generate` — regenerate the Prisma client. **The client is emitted to `prisma/client/`** (not `node_modules/@prisma/client`) per `schema.prisma`, so imports across the codebase are `from 'prisma/client/client'`. Preserve that path when adding files.
- **Airport/terminal/gate geometry is hardcoded** in the resource seed files (`prisma/seed/resource/{airports,terminals,gates}.seed.ts`) as `{ latitude, longitude }` coordinate arrays — there is no fetch script and no generated JSON. The values are sourced manually from OpenStreetMap via the Overpass API — the same data openairportmap.org renders. Coverage varies by tag, so check more than one: perimeters are `aeroway=aerodrome`; terminal footprints are `aeroway=terminal` but some (e.g. Frankfurt T2) are only `building=*`; aircraft stands are usually `aeroway=parking_position` (refs like `A30`, zero-padded `05`) rather than `aeroway=gate`. Some seeded gate names are synthetic and have no OSM stand — leave those on their placeholder coordinate rather than inventing one. To refresh, query Overpass by ICAO code (send a real `User-Agent`; the default `curl`/library UA gets a `406`), assemble multipolygon outer rings, simplify, and paste the coordinates into the seed file, preserving every other field (ids, `operatorCodes`, gate attributes).

Seeded API users (used by the Cucumber REST context; see `features/_context/rest-api.context.ts` and `README.md`): `admin@example.com`, `operations@example.com`, `cabin-crew@example.com`, all with password `P@$$w0rd`.

## Architecture

**Stack:** NestJS 11, Prisma 7 on Postgres 16, `@nestjs/cqrs` for command/query separation, `@nestjs/event-emitter` + `@nestjs/schedule` for async/scheduled work, JWT (EC keys from env) for auth, `class-validator` for request DTOs, Swagger at `/api`.

**Entry:** `src/main.ts` boots `AppModule` on port 3000 and wires input validation, Swagger, Helmet, CORS in that order. `AppModule` composes feature modules plus globals (`CqrsModule.forRoot()`, `EventEmitterModule.forRoot()`, `ScheduleModule.forRoot()`, `CacheModule.register({ isGlobal: true })`, `ConfigModule.forRoot({ isGlobal: true })`).

**Module layout (DDD-flavored, uniform across modules):** each feature module under `src/modules/<name>/` follows this split:

```
application/
  command/   — CQRS CommandHandlers (imperative, return ids/void)
  query/     — CQRS QueryHandlers (read models)
  assert/    — "assert X exists" handlers (existence checks), where present
  event/     — @OnEvent domain-event listeners (internal/ + external/), where present
infra/
  database/  — Prisma-backed repositories (the ONLY place PrismaService is injected)
  http/action/ — one @Controller class per endpoint (thin HTTP → bus) + request DTOs
  service/   — glue to external providers + scheduled (@Cron) work
model/       — domain types / API-shaped classes / error/*.error.ts
<name>.module.ts  — declares action controllers + repositories + every handler
```

Endpoints are **one controller class per endpoint** ("actions") under `infra/http/action/<group>/`, each a thin `@Controller` that translates HTTP → `CommandBus.execute(new XCommand(...))` or `QueryBus.execute(new XQuery(...))`. There are no multi-method controllers. Write-then-read is idiomatic (e.g. `CreateAirportAction` dispatches `CreateAirportCommand` then `GetAirportByIdQuery`). When you add a handler (command/query/assert), you **must** also add it to the module's `providers`, and each new action to `controllers` — neither is auto-discovered. Keep `PrismaService` out of the application layer: command/query/listener handlers read/write via repositories, and cross-module reads go through the bus (a query dispatched to the owning module), never `prisma.*` directly. Repository single-entity fetch is `findById(id)` (id) / `findOneBy(criteria)` (criteria). The `flights` module is the largest reference.

**The `manifest` module** is one module covering everything that says who and what is aboard a flight — the passenger manifest, the cargo manifest and the notification to captain. It holds three repositories (`passengers`, `cargo`, `notoc`) under the one `infra/database/repository/`, its reference data (the commodity catalogue and the hold layouts) under `data/`, and every model for the three concerns under one `model/`. Being one module, the pieces call each other directly rather than over the bus; the bus is still the boundary to everything outside it.

**The `change-requests` module** is the one review queue for crew-proposed edits to curated reference data. Cabin crew propose (`POST airport/:airportId/request-data-change`, and `POST airport/:airportId/{parking-position,gate,terminal,runway}/:id/request-data-change` for the records nested under an airport), operations and admins review (`GET/POST user-data-change-request…`), and the requester follows and withdraws their own (`user/me/data-change-request`, `DELETE user-data-change-request/:id`). Rows are polymorphic — `resource` + `targetId`, no foreign key to the target — and every kind of data plugs in through a `ChangeRequestTarget<R>` adapter (`validate`, `read`, `apply`, plus the whitelist of `fields`); the adapter reaches the owning module only over the bus. Proposals are typed per kind: `ChangeRequestValues` maps each `ChangeRequestResource` to its field types, `ChangeRequestChanges<R>` is the partial of that, handlers work on `TypedChangeRequest<R>` through a generic private method, and `ChangeRequestTargets` holds a `ChangeRequestTargetMap` so a resource without an adapter fails to compile. The only cast is where the JSON `payload` column is read back. Supporting a new kind means a `ChangeRequestResource` enum value, an entry in `ChangeRequestValues`, an adapter and a submit action — never a second queue. Decisions are whole-request and last write wins: accept applies the proposed values regardless of later edits, keeps the overwritten ones in `appliedSnapshot`, and transitions with a conditional `WHERE status = 'pending'` so concurrent decisions resolve to one winner. Airports, parking positions, gates, terminals and runways are the supported kinds. A proposal for a nested record stores only that record's id, so its adapter looks it up by id alone (`FindParkingPositionQuery`, `FindGateQuery`, `FindTerminalQuery`, `FindRunwayQuery`) to learn the airport and applies through the existing airport-scoped `Update*Command`. A proposed terminal is checked with `AssertTerminalBelongsToAirportQuery` and a gate's proposed stand with `AssertParkingPositionExistsQuery`, both 404 like the direct edit. One `*_FIELDS` list per kind (`PARKING_POSITION_FIELDS`, `GATE_FIELDS`, `TERMINAL_FIELDS`, `RUNWAY_FIELDS`) is the single source behind the values type, the adapter whitelist and the request DTO. Every proposal DTO is `PartialType(…, { skipNullProperties: false })` so `null` fails on a column that cannot hold it (a stored proposal like that would only blow up on accept), while fields the model marks `@IsOptional()` stay nullable; a field a proposal DTO declares itself takes `@ValidateIf((_, value) => value !== undefined)`, never `@IsOptional()`, which would let `null` through regardless. The airport adapter applies scalar fields through `UpdateAirportCommand` (never passing `city`, which would find-or-create and rename) and the city through `ReassignAirportCityCommand`.

**Core (`src/core/`):** cross-cutting building blocks — `http/auth` (JWT guard + `@Role(UserRole.X)` and `@SkipAuth()` decorators), `http/{cors,helmet,swagger}` config, `http/response` generic response DTOs, `validation` (`UuidParam`, global pipe config), `provider/{prisma,adsb,simbrief,skylink,discord,weather,aerolopa}` external integrations (all provider clients fetch through `provider/http/fetch-with-retry.ts` for timeout + retry), plus `errors`, `domain/events`, `cache`, `utils`. Reach for these before adding bespoke utilities in a module.

**Config:** DI code reads env via `ConfigService` (`getOrThrow` for required keys); only genuinely pre-DI/bootstrap spots use `process.env` (the `app.module` scheduler flag, `PrismaService` — which is also `new`'d in seed scripts — and the bootstrap CORS/Helmet `NODE_ENV`, shared with decoration-time WS-CORS).

**Auth model:** all endpoints require JWT by default; opt out with `@SkipAuth()`. Role gating is `@Role(UserRole.Operations)`, where `UserRole` is the domain enum at `src/modules/users/model/user-role.ts` (imported relatively; it mirrors the Prisma enum's shape). Do not import `UserRole` from `prisma/client/*`. Every token also carries a `client` claim — `web` or `transponder`, the `SessionClient` enum in `src/modules/auth/model/session-client.ts`; a token without one counts as `web`. `ClientGuard` (between the JWT and roles guards) refuses a Transponder token with `403` everywhere except `@SkipAuth()` routes and handlers marked `@AllowClient(SessionClient.Transponder)`, and the flight-events WebSocket refuses it too. Mark an endpoint only when the Transponder actually calls it, and cover it with a scenario using `I am signed in to the Transponder as`. The Transponder signs in only through the device flow — `POST auth/device`, approved on the web app's `/activate` page, then polled at `POST auth/device/token` — and only a Transponder token may send `source: gsx`. Transponder sessions last 90 days, browser sessions 7; `GET user/me/session` lists them and `DELETE user/me/session/:id` revokes one.

**Error handling:** every error surfaces through one global filter — `DomainExceptionFilter` in `src/core/errors/domain-exception.filter.ts`, registered in `main.ts` via `configureExceptionHandling(app)`. Throw typed domain errors that extend the category classes in `src/core/errors/domain-error.ts` (`BadRequestError`→400, `UnauthorizedError`→401, `ForbiddenError`→403, `NotFoundError`→404, `ConflictError`→409, `UnprocessableError`→422); define the concrete errors under each module's `model/error/*.error.ts` (e.g. `class FlightNotFoundError extends NotFoundError`). The filter maps the error's category to the HTTP status and emits one canonical body — `{ statusCode, error, message, violations? }` — where `statusCode` always equals the HTTP status and `error` is the reason phrase. Do **not** throw `@nestjs/common` HttpExceptions directly from domain, application, or infra code — every error is a typed class extending a `DomainError` category (defined per module in `model/error/*.error.ts`, or alongside a provider client). The only intentional framework-level exceptions left are the JWT/roles **guards** (their bare `401`/`403`) and the global **validation pipe** (`400` with a `violations` map); leave those as-is. The old `{ statusCode, error, message }` constant objects (`errors.dto.ts`) have been removed — never reintroduce that pattern. Note the canonical reason phrase for `422` is `"Unprocessable Content"` (from the filter), not Nest's default `"Unprocessable Entity"`.

**External providers are mocked in dev:** `ADSB_API_HOST`, `SKYLINK_API_HOST`, `SIMBRIEF_API_HOST`, `WEATHER_API_HOST`, `GOOGLE_JWKS_URI` point at the single `mock` container in `compose.yaml` (Mockoon) through network aliases such as `adsb-mock`. Each environment file in `docker/mock/` runs on its own port (`1080`–`1090`), with larger response bodies in a folder named after it. The provider **functions** — `AEROLOPA_FUNCTION_BASE_URL`, `OSM_FUNCTION_BASE_URL`, `POSTCARD_FUNCTION_BASE_URL` and `OCEANIC_TRACKS_FUNCTION_BASE_URL` — use the `functions-mock` alias on ports `1087`, `1088`, `1089` and `1090`. Their function routes require the `X-Require-Whisk-Auth` secret and answer `401` without it, the way the platform does. `prisma/seed/resource/cabin-layout-versions.seed.ts` reads `docker/mock/functions/aerolopa.json` and its `aerolopa/` body files directly, so moving them breaks the seed. The web app's Vite dev server proxies postcard art to `localhost:1089`. Discord is split in two: `DISCORD_API_HOST` points the REST/OAuth client (`DiscordIdentityClient`) at `discord-mock`, while the bot **gateway** (`DiscordGateway`, discord.js) has no mock — it connects under `NODE_ENV=production` or `DISCORD_GATEWAY_ENABLED="true"` and refuses otherwise. Message delivery is gated on `NODE_ENV` alone, so outside production `TestDiscordClient` always writes each message to `test-data/discord/<type>_<flightId>.md`; `findMembership` answers `unknown` only while the gateway is off (enabling it makes the seeded membership scenarios report `not_member`, so keep the flag off when running the functional suite) — see **docs/DISCORD.md**.

**AeroLOPA (`src/core/provider/aerolopa/`):** seat maps come from a DigitalOcean Function in the sibling `mypreflight-aerolopa-provider` repo — the API side is an HTTP client and nothing else (no persistence, no scraping). One `GET` carries `op=seatmap|resolve|configurations` plus an `X-Require-Whisk-Auth` secret; `AerolopaClient` exposes `getSeatMap(slug)`, `resolve(airline, aircraft, includeSeatMaps?)` and `listConfigurations()`. `type/aerolopa.types.ts` is **hand-written** and mirrors the vendored `aerolopa.openapi.json` by hand — there is no codegen and no CI drift gate, so when the contract changes, update both (keep the types comment-free; the descriptive prose belongs in the contract). Upstream error codes map to typed errors in `error/aerolopa.error.ts`: `SEAT_MAP_NOT_FOUND`/`SEAT_MAP_UNREADABLE` only on calls that carry a slug, everything else (rejected secret, timeout, upstream 5xx) collapses into `AerolopaUnavailableError`. AeroLOPA is keyed by airline + cabin configuration with **no registration index**, so `resolve()` is often `ambiguous` — the plan is a curated cabin-configuration field on the aircraft rather than a per-request lookup.

**OpenStreetMap (`src/core/provider/osm/`):** airport infrastructure — boundary, runways, terminals, parking positions and gates — comes from a DigitalOcean Function in the sibling `osm-provider` repo, and the API side is an HTTP client and nothing else. `OsmClient.pullAirport(icao)` is a read: the function holds no credentials for this API and writes nothing. `type/osm.types.ts` is **hand-written** and mirrors the vendored `osm.openapi.json` by hand, exactly as the AeroLOPA types do — no codegen, no drift gate, so update both together. `AERODROME_NOT_FOUND` and `RESULT_TOO_LARGE` map to typed errors; everything else (rejected secret, timeout, Overpass down, a bare `404` from something that is not the function) collapses into `OsmProviderUnavailableError`.

**Oceanic tracks (`src/core/provider/oceanic-tracks/`):** today's organised oceanic tracks come from a DigitalOcean Function in the sibling `oceanic-tracks-provider` repo, which holds the FAA NOTAM service key, reads the track messages and places every fix. The API side is an HTTP client and nothing else. `OceanicTracksClient.listTracks()` takes no arguments. `type/oceanic-tracks.types.ts` is **hand-written** and mirrors the vendored `oceanic-tracks.openapi.json` by hand, exactly as the AeroLOPA types do, so update both together. Every failure (rejected secret, timeout, the FAA down or refusing) collapses into `OceanicTracksUnavailableError`. The `oceanic-tracks` module serves the tracks at `GET api/v1/oceanic-track` without sign-in and keeps the function's raw answer in the global cache for 15 minutes (`CACHE_KEYS.OCEANIC_TRACKS`), mapping it on every read. That cache is what keeps the FAA's limit of one data pull every 3 minutes however many people open the map, so don't shorten it or add a second caller.

**The OpenStreetMap data upgrade (`airports` module, `airport/:id/enrich`):** an operations user `GET`s `enrich`, which reads OpenStreetMap, compares it against the airport and answers a proposal — one selectable change per record, each with a stable `<resource>:<label>` key, a status of `added`/`removed`/`updated`/`not-changed`, the fields that would be written with current beside proposed, and the `requires` a dependency needs. Nothing is written. The pull is retained in the global cache for an hour (`airportOsmPullCacheKey`), so a repeated review costs Overpass nothing; `?refresh=true` insists on fresh data. `POST`ing the same path with the keys the reviewer accepted applies exactly those: it rebuilds the proposal from the retained pull rather than trusting the request, so what lands is what was reviewed, and it answers `409` when no pull is held. Pushing a `removed` key **deletes** that record — which is why nothing is ever applied unselected.

The comparison lives in `model/osm-upgrade.diff.ts` and is pure, with `model/osm-upgrade.diff.spec.ts` covering it. Three rules there are deliberate and easy to break: a runway's `magneticHeading` and `lightingType` are written on create and never diffed (the provider derives the heading from the designator and always reports lighting as `unknown`, so patching would replace surveyed data with a placeholder); an `unknown` surface, a `remote` stand and a null gate-to-stand link are silence from OpenStreetMap, never evidence, so none of them overwrites a curated value; and a terminal's name, taxi time, operators and notes are create-only. Boundary rings compare as point sets, because OpenStreetMap may rewind a way without the boundary moving. `dataQuality` is never touched — it is an editorial grade, per the `airport-data-curation` spec.

**Google and Discord sign-in are both link-only** — **docs/DISCORD.md** describes the Discord behaviour; the config, endpoints, token verification and test fixtures live in `.env.dist`, the auth module and its features (the prose contract that used to sit in README § Discord was dropped when the README became product-facing). The two constraints that bite when editing code: `User.password` is nullable, so any credential path must reject null-password users before reaching bcrypt; and `POST /api/v1/auth/google` resolves users by `googleId` only — never add an email fallback, it reintroduces an account-takeover path. The same holds for `POST /api/v1/auth/discord` and `discordId`, which is why `discordId` is absent from every request DTO: it is an authentication identifier, so only a completed OAuth exchange may write it. Errors that need a 5xx use `BadGatewayError` (502) — the only non-4xx `DomainError` category.

**Functional tests (`features/`):** Gherkin organized by domain (`airport/`, `flight/`, `operator/`, `aircraft/`, `rotation/`, `auth/`, `skylink/`, `user/`). Shared step definitions live in `features/_context/`: `rest-api.context.ts` (sign-in + generic `I send a <METHOD> request to <path>` + `response body should contain` deep-compare via `features/_helper/deep-compare.ts`), `database.context.ts` (reset hooks + `I set database to initial state`), plus contexts for ADS-B and Discord. Add new steps to an existing context file when the vocabulary matches; create a new one only for a genuinely new subsystem.

**Prisma specifics:** `schema.prisma` sets `generator client { output = "../prisma/client" }`, so every import is `from 'prisma/client/client'` (types, enums like `UserRole`, `Continent`). Seed entrypoint is `prisma/seed/seed.ts`; resource fixtures under `prisma/seed/resource/` feed `loadResources()`, which is reused by both the seed script and the Cucumber `I set database to initial state` step. Dev and CI end up on `prisma db push` (the entrypoint's seed step force-resets the schema), while production only ever runs `prisma migrate deploy`, so the suite never exercises what a migration wrote and a hand-edited foreign key can drift unnoticed. To check, point `DATABASE_URL` at an empty scratch database, run `npx prisma migrate deploy`, then `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code`; exit code `2` means drift.
