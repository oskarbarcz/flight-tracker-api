## Context

See proposal.md — Why. The relevant constraints already in place:

- A Discord bot exists (`DiscordGateway`, discord.js) and holds a gateway connection
  under production or an explicit flag. It sends announcements and briefings.
- Google Sign-In established the link-only pattern: an identity provider grants a
  session on an already-linked account and never creates one. `User.password` is
  already nullable, so provider-only accounts exist.
- Every external provider client fetches through `provider/http/fetch-with-retry.ts`,
  and every error is a typed class extending a `DomainError` category.

Discord differs from Google in one way that drives most of this design: it issues no
browser-side ID token. There is nothing the frontend can hand over that the API can
verify on its own — only an authorization code that must be exchanged for a token
using a client secret the frontend must not hold.

## Goals / Non-Goals

**Goals:**

- Make `discordId` trustworthy enough to authenticate with, by making the API the only
  party that can write it.
- Keep the bot and the OAuth client as one Discord application but two independent
  code paths, so that a broken gateway does not break linking and vice versa.
- Let a user link and join the server in a single consent pass.

**Non-Goals:**

- Storing Discord tokens or acting on a user's behalf later. Nothing beyond the link
  request needs the user token.
- Role or permission mapping from Discord server roles.
- Receiving from Discord. The bot keeps its receive-side intents but nothing listens.

## Decisions

**The API performs the code exchange, not the frontend.** The frontend redirects the
whole page, gets a `code` back on its callback route, and posts it to the API. The
alternative — a frontend-side exchange — would require shipping the client secret to
the browser, which forfeits the entire point of using OAuth to establish identity.
PKCE (`code_verifier`) is generated by the frontend and passed through, so the code is
useless to an interceptor even before it reaches the API.

**The redirect URI is validated against a configured allowlist before the exchange.**
Discord validates the redirect URI too, but only against the portal registration,
which may legitimately hold several URIs. Checking our own allowlist first means a
code obtained for one registered callback cannot be replayed against another. It is
config (`DISCORD_OAUTH_REDIRECT_URIS`), not a constant, because the deployed frontend
origin differs per environment.

**A separate `DiscordIdentityClient`, not an extension of the gateway client.**
Linking talks REST (`/oauth2/token`, `/users/@me`, `/guilds/*/members/*`); the bot
talks websocket. Keeping them apart means linking works with the gateway off — which
is the normal local and test configuration — and lets the REST side be pointed at a
mockserver (`DISCORD_API_HOST`) while the gateway simply stays offline. discord.js
offers no useful abstraction over the OAuth endpoints anyway.

**The join happens inside the link request.** `guilds.join` needs the _user_ access
token alongside the bot token, and we deliberately do not store the user token. The
alternative — storing a refresh token so a user could join later — trades a permanent
credential at rest for a convenience that an invite link already covers. So the choice
is: join now, or re-link later.

**A failed join does not fail the link.** They are independent facts, and a link is
useful on its own (sign-in works, the profile is populated). Rolling the link back
because the bot lacked _Create Invite_ would be a worse outcome than reporting
`joinOutcome: failed` and letting the user join by hand. The link response therefore
carries the join outcome as its own field rather than as an error.

**Membership is a tri-state with `unknown`, and `unknown` absorbs every failure.**
Membership is read through the gateway's cache of the guild. With the gateway off, or
Discord silent, or no account linked, the honest answer is that we do not know.
Collapsing that to `not_member` would make an account screen tell a member they are
not one, and would invite a UI to offer a join the user does not need.

**Identity attributes are denormalised onto `user`.** `discordUsername`,
`discordGlobalName` and `discordAvatar` are stored at link time so that
`GET /api/v1/user/me` can render the linked account without a Discord round trip on
every profile read. The cost is staleness — a user who renames on Discord sees the old
name until they re-link. That is acceptable for a display label; the identifier that
actually matters (`discordId`) never changes.

**`BadGatewayError` (502) is introduced.** An unreachable Discord is not the caller's
fault, and every existing `DomainError` category maps to a 4xx. This is the first and
only non-4xx category.

**`DISCORD_GATEWAY_ENABLED` is separate from the delivery gate.** Connecting the
gateway locally is useful for exercising membership against a real server; _sending_
messages from a dev box is not. So connection is gated on `NODE_ENV=production` or the
flag, while delivery stays gated on `NODE_ENV` alone — outside production every
message is still written to `test-data/discord/` and no test run can post to a real
server.

## Risks / Trade-offs

- **The client secret is a new secret at rest.** → It lives only in environment
  config, never in the repo; `.env.dist` carries a placeholder. Rotating it in the
  developer portal is the recovery path if it leaks.
- **Removing `discordId` from `PATCH /api/v1/user/me` is breaking.** → It is the point
  of the change: a self-declared authentication identifier is a takeover path. The
  field was recent and the replacement endpoint ships in the same change.
- **Denormalised Discord profile data goes stale.** → Accepted, as above; re-linking
  refreshes it.
- **The join needs the bot to hold _Create Invite_ in the server.** → A missing
  permission surfaces as `joinOutcome: failed` rather than a broken link, and is
  documented in README as a setup step.
- **Membership depends on the gateway's guild cache.** → Reported as `unknown` when
  the gateway is offline, so the failure mode is a missing answer rather than a wrong
  one. The functional suite runs with the gateway off and asserts `unknown`.

## Migration Plan

The migration adds four nullable columns (`discordUsername`, `discordGlobalName`,
`discordAvatar`, `googleEmail`); `discordId` already exists and stays nullable. There
is no backfill: existing self-declared `discordId` values remain and keep receiving
briefings, but they were never verified, so no new trust is extended to them — a user
who wants Discord sign-in must complete a real link. Rollback is dropping the four
columns; the endpoints are additive apart from the removed `discordId` input, which a
rollback would restore.
